# Looma

Looma는 QA 엔지니어가 프로젝트의 테스트 업무를 정리하고 이어가기 위한 개인 업무 도우미입니다. 기존 테스트 자산을 기준으로 요구사항의 변경, TC 검토, 수행 결과와 확인사항을 연결해 관리하는 한국어 웹앱을 만들고 있습니다.

## Looma가 다루는 흐름

```mermaid
flowchart LR
    A[산출물] --> B[요구사항]
    B --> C[테스트 조건]
    C --> D[TC]
    D --> E[수행 결과]
    E --> F[이슈와 기록]
```

변경된 산출물이 들어오면 기존 요구사항과 테스트 자산을 기준으로 영향을 살피고, TC 변경안을 검토한 뒤 반영하는 흐름을 지향합니다. 전체 TC를 다시 만드는 대신 기존 자산을 유지하면서 바뀐 부분을 이어가는 것이 목표입니다.

현재는 업로드한 문서 내용을 자동 분석해 요구사항이나 변경안을 생성하는 기능은 연결하지 않았습니다. 변경 영향 검토와 변경안의 검토 및 반영 흐름은 예시 데이터와 현재 프로젝트 데이터 구조를 통해 사용할 수 있습니다.

## 주요 기능

- **프로젝트와 테스트 자산** — 프로젝트별로 산출물의 파일 이름, 링크와 버전을 등록하고 요구사항과 TC를 확인합니다. 요구사항, 테스트 조건, TC의 연결을 관리하고 TC의 근거 산출물을 표시합니다.
- **요구사항 파일 가져오기와 기본 TC 초안** — 정리된 요구사항 표(CSV/XLSX)를 열 매핑과 미리보기를 거쳐 요구사항으로 가져옵니다. 요구사항 화면에서 요구사항과 테스트 관점을 골라 요구사항 문장만 근거로 한 기본 TC 초안과 테스트 조건을 만들 수 있으며, 미리보기에서 확인 필요 · 제외를 확인하고 같은 내용의 TC가 이미 있으면 기존 TC와 연결 · 별도 신규 · 제외 중에서 직접 고른 뒤에만, 미리보기와 같은 내용일 때만 저장합니다. 이 초안은 기본적으로 규칙 기반이며, 사용자가 버튼을 눌렀을 때만 AI 초안으로 바꿔 볼 수 있습니다([AI TC 초안](#ai-tc-초안-groq) 참고). 기존 TC는 바꾸지 않고, 고객사 TC ID는 만들지 않습니다.
- **변경 영향 검토** — 요구사항 변경과 TC의 신규, 수정, 유지, 폐기 제안을 검토하고 반영합니다. 중복 후보는 기존 TC 수정, 별도 생성, 제외 중 처리 방법을 사용자가 결정하며, 미결정 항목이나 판단 간 충돌이 있으면 반영을 막습니다.
- **TC와 수행 결과 가져오기** — CSV/XLSX의 열을 매핑하고 기존 TC와의 연결이나 변경 내용을 검토합니다. Excel 등에서 수행한 결과는 TC 정의를 바꾸지 않고 별도 기록으로 가져오며, PASS, FAIL, BLOCKED, 미수행을 기능과 플랫폼별로 요약합니다.
- **이슈와 확인사항** — FAIL · BLOCKED 결과나 수행 결과 비교의 신규 실패 · 계속 실패 · 신규 차단 행에서 결함(이슈)과 사양 · 정책 확인사항을 직접 만들어, 어떤 TC의 어느 차수 · 플랫폼 결과에서 나왔는지 연결해 둡니다. 상태는 확인 필요 · 해결됨 · 보류로 관리하며, 이후 차수에서 PASS가 나와도 자동으로 해결 처리하지 않습니다.
- **추적성과 이력** — 요구사항에서 테스트 조건과 TC로 이어지는 관계, 가져온 파일의 행과 TC의 연결을 유지합니다. 가져오기 이력과 프로젝트 활동 기록에서 처리한 내용을 다시 확인할 수 있습니다.
- **개인 작업공간** — 오늘의 할 일, 임시 메모, 용어 사전을 함께 제공합니다. 데스크톱 중심의 반응형 화면과 라이트/다크 테마를 지원합니다.
- **로컬 저장** — 앱 상태는 브라우저 IndexedDB에 저장하고, TC와 수행 결과 가져오기의 원본 파일 bytes는 별도 저장소에 보존합니다. 처음 실행할 때 예시 데이터를 만들며, 현재 서버 저장과 기기 간 동기화는 제공하지 않습니다.

## AI TC 초안 (Groq)

요구사항 화면의 TC 초안 만들기에서 **AI로 TC 초안 생성** 버튼을 눌렀을 때만 외부 AI(기본: Groq `openai/gpt-oss-120b`, 무료)가 초안을 만듭니다. 규칙 기반 초안은 그대로 기본이며, AI가 실패해도 계속 쓸 수 있습니다.

```
요구사항 → AI 초안(후보) → 분석(중복 · 확인 필요 · 지문 · 추적성) → 사람이 검토 → 명시적 적용 → TC
```

- AI 응답은 후보일 뿐입니다. 적용하기 전에는 아무것도 저장하지 않고, 적용해도 기존 TC · 테스트 조건은 바꾸지 않습니다. 새 TC는 `초안` 상태, 출처 `ai_generated`, 근거 유형 `ai_suggestion`(확인 필요 요구사항이면 `needs_confirmation`)으로 만들어집니다.
- 요구사항 ID · 기능명 · 근거 위치는 AI가 아니라 저장된 요구사항에서 가져옵니다. 요청하지 않은 요구사항 ID · 관점의 초안은 버립니다. AI 초안을 받은 뒤 요구사항이 바뀌면 그 초안은 쓸 수 없고 다시 만들어야 합니다.
- 외부로 보내는 데이터는 선택한 요구사항의 ID · 기능 · 문장 · 확인 필요 여부와 테스트 관점뿐입니다. 산출물 파일 · 근거 위치 · 기존 TC · 다른 프로젝트 데이터는 계약에 없어 보낼 수 없고, 화면에서 보낼 목록을 호출 전에 보여 줍니다.
- 한 번에 요구사항 5개 · 관점 3개까지(Groq 무료 한도 `8K TPM`에 맞춘 작은 배치), 요청 16KB, 출력 4,000토큰, Groq 대기 20초, 자동 재시도 없음입니다. TC 수천 건의 일괄 생성은 지원하지 않습니다.
- OpenAI(유료)는 설정에서 `추후 활성화`로 표시되는 자리만 있고 호출 경로가 없습니다. 무료 한도(429)나 오류가 나도 다른 공급자로 자동 전환하지 않습니다.

### 서버 함수와 접근 제어

Groq API 키는 Vercel 서버 함수(`api/ai/test-drafts.ts`)에서만 읽고 브라우저에는 내려가지 않습니다(`VITE_` 접두사 환경변수를 쓰지 않습니다). Looma에는 사용자 로그인이 없으므로, 서버 환경변수 `LOOMA_AI_ACCESS_CODE`와 같은 **접근 코드**를 아는 사용자만 이 함수를 쓸 수 있습니다.

- 환경변수가 없거나 24자보다 짧으면 모든 요청을 거부합니다(fail-closed). 코드가 틀리거나 없으면 Groq를 호출하지 않습니다.
- 코드는 SHA-256으로 만든 뒤 상수 시간으로 비교합니다. 같은 접속자가 10번(접속자 구분 없이 서버 전체 60번) 틀리면 1분간 맞는 코드도 비교하지 않고 거부합니다. 공격 중에는 정상 사용도 잠시 막힐 수 있습니다.
- 설정 화면의 접근 코드 입력칸은 이 앱의 서버 함수용 코드를 받는 곳이며 **Groq · OpenAI API 키를 입력받지 않습니다.** 코드는 `sessionStorage`에만 저장돼 탭을 닫으면 사라지고, URL · 로그 · 오류 메시지에 넣지 않습니다.
- 서버 로그에는 오류 분류(`timeout`, `rate_limited` 등)만 남기고 키 · 접근 코드 · 요청 · 응답 내용은 남기지 않습니다.

**알려진 한계 — 완전한 사용량 보호가 아닙니다.**

- 접근 코드는 공유 비밀번호일 뿐 사용자 인증이 아닙니다. 코드가 새면 누구나 같은 권한으로 호출할 수 있고, 사용자별로 구분하거나 취소할 수 없습니다. 코드가 의심되면 Vercel에서 값을 바꾸고 재배포하세요.
- 분당 호출 수 · 동시 실행 수 · 실패 횟수 제한은 서버리스 인스턴스 메모리에만 있습니다. 인스턴스가 여러 개 뜨거나 새로 뜨면 따로 세므로 **전체 사용량의 상한이 아닙니다.** 최종 상한은 Groq 계정 쪽 한도(무료 플랜)이며, 필요하면 Vercel Deployment Protection 등 별도 보호를 함께 쓰세요.
- 브라우저에 저장된 접근 코드는 페이지에서 실행되는 악성 스크립트(XSS)에 노출될 수 있습니다.

### Vercel 설정

Vercel 프로젝트 → Settings → Environment Variables에 두 값을 등록합니다(Production과 Preview에 필요한 환경을 선택). 값은 코드 · Git · 채팅에 적지 않습니다.

| 이름 | 값 |
| --- | --- |
| `GROQ_API_KEY` | Groq 콘솔에서 발급한 키 |
| `LOOMA_AI_ACCESS_CODE` | 24자 이상 무작위 값. 예: `node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"` |

환경변수를 바꾼 뒤에는 새로 배포해야 적용됩니다. 변수 이름만 적은 예시는 [`.env.example`](.env.example)에 있습니다.

Preview 배포가 Vercel Authentication으로 보호되어 있어도 그대로 두면 됩니다. 로그인한 브라우저에서 Preview를 열면 같은 주소로 보내는 AI 요청에 Vercel 인증 쿠키가 함께 가서 보호를 통과하고, 그 뒤에 접근 코드를 검사합니다. 보호를 끄거나 우회 키를 앱에 넣을 필요는 없습니다. 보호 단계에서 막히면 접근 코드 오류가 아니라 Vercel의 `401`(`Protected by Vercel Authentication`)이 응답 본문에 보입니다.

로컬 `npm run dev`(Vite)는 서버 함수를 실행하지 않아 AI 버튼이 "서버 함수를 쓸 수 없어요"로 안내합니다. 서버 함수까지 확인하려면 `vercel dev`로 실행하고 `.env.local`에 위 두 값을 넣으세요(`.env.*`는 Git에서 제외됩니다).

### 실제 Groq 호출을 안전하게 확인하기

1. 배포 URL에서 접근 코드 없이 호출해 거부되는지 먼저 봅니다. Groq 호출 없이 `401`이어야 합니다.

   ```bash
   curl -i -X POST https://<배포 주소>/api/ai/test-drafts -H "content-type: application/json" -d "{}"
   ```

2. 설정 → AI 초안에서 접근 코드를 입력합니다.
3. 프로젝트의 요구사항 화면에서 **요구사항 1개 · 관점 1개**만 골라 TC 초안 만들기를 열고 AI 버튼을 한 번 누릅니다. 호출 1회라 무료 한도(Groq 문서 기준 `openai/gpt-oss-120b`는 분당 8K 토큰, 일 200K 토큰이며, 계정의 실제 한도는 Groq 콘솔 limits 페이지에서 확인)에 미치는 영향이 작습니다.
4. 미리보기를 확인하고 마음에 들지 않으면 **만들기를 누르지 않고 닫습니다.** 닫기만 하면 저장되는 것이 없습니다.

## XLSX 가져오기와 내보내기

고객사에서 사용하는 XLSX 양식을 최대한 유지하기 위해, 가져온 원본 bytes를 보존하고 기존 행의 변경된 셀을 OOXML 수준에서 수정합니다. SheetJS는 파일을 읽고 결과를 확인하는 데 사용하며, 내보낼 때 전체 통합 문서를 SheetJS로 다시 쓰지 않습니다.

Looma에서 만든 신규 TC는 검토가 끝나고 다시 가져왔을 때 구별할 수 있는 경우에만 기존 표 끝에 추가합니다. 고객사 TC ID가 없으면 ID 칸을 비워 두며, Looma가 임의로 고객사 ID를 만들지 않습니다.

Excel 표(table), 자동 필터(autoFilter), 수식이나 병합 범위 등으로 새 행의 위치와 의미를 안전하게 유지할 수 없으면 행 추가를 막고 제외 이유를 표시합니다. 이때 기존 셀 수정이 안전하면 해당 수정만 내보낼 수 있습니다. 지원하지 않는 셀 수정이나 내보낸 파일의 재검증 실패는 다운로드를 중단하는 방식으로 처리합니다.

## 설계 원칙

- 기존 TC 세트를 지속적으로 유지하는 기준 자산으로 둡니다.
- 변경된 부분을 중심으로 제안을 검토하고, 명시적인 판단을 거쳐 반영합니다.
- 요구사항이 제거되어도 TC를 즉시 삭제하지 않고 폐기 여부를 별도로 검토합니다.
- 요구사항, 테스트 조건, TC 사이의 추적성을 유지하고 TC 정의와 수행 결과 기록을 분리합니다.
- 파일 구조를 안전하게 다룰 수 없으면 추측해서 내보내지 않습니다.

ISO/IEC/IEEE 29119의 테스트 설계 및 추적성 개념을 참고한 구조입니다.

## 기술 스택

- React, TypeScript, Vite, React Router
- CSS Modules와 CSS 변수 토큰, lucide-react, Pretendard
- IndexedDB, SheetJS, OOXML 수정 모듈
- Vercel Functions(AI 초안 서버 함수), Groq API
- Vitest, Playwright, GitHub Actions

## 실행 방법

Node.js 24와 npm을 사용합니다. Node 버전은 [`.nvmrc`](.nvmrc)에 지정되어 있습니다.

```bash
git clone https://github.com/yoobilee/looma.git
cd looma
npm ci
npm run dev
```

전체 검증을 실행하려면 Chromium 테스트용 브라우저를 먼저 설치합니다.

```bash
npx --no -- playwright install --only-shell chromium
npm run verify
```

## 검증

`npm run verify`는 Lint, Type Check, 단위 테스트, 브라우저 테스트, Build를 순서대로 실행합니다. Vitest로 변경안 반영, 파일 가져오기, 추적성, XLSX 수정과 신규 행 추가 등 도메인 로직을 검증하고, Playwright 기반 Chromium 테스트로 실제 IndexedDB의 저장과 트랜잭션 동작을 확인합니다.

GitHub Actions도 PR과 main push에서 같은 검증 명령을 실행합니다. 브라우저 자동 검증의 현재 범위는 IndexedDB 회귀 테스트입니다.

## 프로젝트 상태

개인 프로젝트로 개발 중입니다. 현재는 로컬 데이터 기반으로 QA 작업 흐름을 구현하고 있으며, 문서 분석과 AI 기반 변경안 생성은 아직 연결하지 않았고, AI는 요구사항 기반 TC 초안 생성에만 선택적으로 연결돼 있습니다.
