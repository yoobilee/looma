# 체계적 디버깅 정책

## 목적

증상에 임시 수정을 반복하지 않고 재현 가능한 근거를 통해 최초 원인을 찾은 뒤 최소 범위로 해결한다.

## 적용 대상

- 버그와 예상하지 못한 동작
- Test, Lint, Type Check와 Build 실패
- 성능 저하와 간헐적 실패
- API, 데이터베이스, 외부 서비스와 배포 환경의 연동 문제

## 1. 문제 재현과 범위 확인

1. 기대 결과와 실제 결과를 구분해 적는다.
2. 재현 단계, 입력값, 환경, 발생 빈도와 최초 발견 시점을 확인한다.
3. 오류 메시지와 경고, 전체 스택 추적을 끝까지 읽고 파일·줄·오류 코드를 기록한다.
4. 최근 diff, 커밋, 의존성, 설정과 환경 차이를 확인한다.
5. 재현되지 않으면 추측으로 수정하지 않고 추가 로그와 조건을 수집한다.

## 2. 근거 수집과 원인 위치 좁히기

- 같은 저장소에서 유사하게 정상 동작하는 코드를 찾아 실패 코드와 비교한다.
- 입력부터 실패 지점까지 데이터와 상태가 변하는 경계를 따라간다.
- 여러 계층이 연결되면 각 경계의 입력·출력과 설정 전달 여부를 확인한다.
- 로그에는 필요한 최소 정보만 남기고 API 키, 토큰, 비밀번호, 개인정보와 원문 데이터를 노출하지 않는다.
- 증상과 확인된 사실, 아직 확인하지 않은 추정을 구분한다.

## 3. 가설 검증

1. “원인은 X이며 근거는 Y다” 형태로 하나의 가설을 세운다.
2. 한 번에 변수 하나만 바꾸는 가장 작은 실험으로 검증한다.
3. 가설이 틀리면 변경을 겹쳐 쌓지 않고 새 근거로 다시 분석한다.
4. 원인을 이해하지 못했으면 아는 것처럼 단정하지 않고 조사 범위와 부족한 정보를 밝힌다.

## 4. 수정

- 가능한 경우 수정 전에 기존 증상을 재현하는 실패 테스트를 만든다.
- 증상이 아니라 확인된 최초 원인을 수정한다.
- 한 번에 하나의 최소 수정만 적용하고 관련 없는 정리나 리팩터링을 섞지 않는다.
- 수정 후 기존 증상, 회귀 테스트와 관련 전체 검증을 실행한다.
- 데이터·인증·권한·결제·개인정보와 관련되면 실패 경로와 롤백 방법까지 확인한다.

## 5. 반복 실패 처리

- 수정이 실패하면 새 정보와 함께 1단계부터 다시 분석한다.
- 서로 다른 수정 시도가 세 번 실패하면 네 번째 수정을 바로 시도하지 않는다.
- 결합도, 공유 상태, 데이터 구조와 외부 의존성 등 구조적인 문제가 아닌지 검토한다.
- 구조 변경이 필요하거나 영향 범위를 확정할 수 없으면 현재 근거, 시도한 내용과 선택지를 사용자에게 보고하고 판단을 받는다.
- 안전성·보안성에 영향이 없는 간헐적·사소한 문제만 `.ai/policies/verification.md` 기준에 따라 백로그로 이관할 수 있다.

## 완료 기록

- 원인과 이를 뒷받침한 근거
- 적용한 최소 수정과 변경 범위
- 재현 여부와 실제 검증 결과
- 실패한 접근과 다시 사용하면 안 되는 이유
- 남은 위험과 백로그 항목
